# DIY retexturing from commercial-clean 2D image models (state as of 2026-10-08)

Scope: text-/image-prompted generation of geometry-aligned views (depth / normal / canny control), multi-view-consistent editing of rendered views, and the open projection-and-inpaint / latent-sync implementations, with the base models that could drive them on the target stack (Win 11 native, 16 GB VRAM, torch 2.8 cu128, sm_120, SDPA only, no nvdiffrast/nvdiffrec, own pure-torch UV rasterizer + depth-tested back-projection already present). Licence policy: MIT/Apache/BSD/OpenRAIL++/NVIDIA Open Model/Llama 3 allowed; FLUX non-commercial, Qwen-Image 2.1 research licence, Hunyuan (outside the experimental engine), nvdiffrast, SMPL-derived banned.

Research-method note: ~45 tool calls (searches + page fetches). Primary sources were preferred (HF model cards, GitHub READMEs, arXiv HTML). Where only aggregator or marketing pages were available this is flagged inline.

## KQ1. Shortest clean path to "text prompt + existing mesh -> new 2K PBR texture on the same UVs" with FLUX.2-klein-4B and Z-Image-Turbo; which adapter gives depth/normal control today

### Takeaway
As of October 2026 the only Apache-2.0 geometry-control adapters for the two models already in the pipeline are (a) Alibaba-PAI's **Z-Image-Turbo-Fun-Controlnet-Union 2.1** (canny/depth/pose/MLSD/HED/scribble/gray + separate Tile model + inpaint mode; no normal control; runs through the Apache-2.0 VideoX-Fun code, not core diffusers) and (b) one community LoRA, **thedeoxen/refcontrol-FLUX.2-klein-4B-reference-depth-lora** (Apache-2.0 on the HF card; depth map + reference image through klein's multi-reference slots; trained on the undistilled klein-base-4B). FLUX.2 klein has no official ControlNet or Control-LoRA at all; the documented trick is to pass a depth map as a `reference_latents` image. The shortest clean path is therefore: Blender depth (+canny) renders of the game mesh from 6-10 cameras -> Z-Image-Turbo + Fun-ControlNet-Union (8 steps, control scale 0.65-1.0) per view (synchronised, see KQ2) -> the project's own depth-tested back-projection into the existing UVs -> PBR split (albedo/roughness/metal) is **not** provided by any of these 2D models and must come from a separate decomposition step (StableGen uses Marigold IID + StableDelight nodes for exactly this).

### Inferences
- Clean depth control exists today for Z-Image-Turbo (Fun-ControlNet-Union 2.1, incl. inpaint and a Tile SR model) and, more weakly, for FLUX.2-klein-4B (one community depth LoRA + the official "depth as reference_latents" trick). **Neither has a normal-map control**; Blender normal renders can only be used via canny/scribble-style edge maps or, for SDXL, the xinsir union (which has Normal). For the "new reference image -> retexture" case, the refcontrol-4B depth LoRA is the only adapter that natively takes both a reference and a depth map; its 50-step/guidance-4 recipe on the base model costs roughly 12x the compute of distilled klein (4 steps).
- Z-Image-Turbo path dependencies: the official pipeline is VideoX-Fun (Apache-2.0, plain PyTorch; Windows tested by the authors on torch 2.2, so torch 2.8 is untested but there is no custom CUDA op in the control transformer as far as the sources show). Running it inside the project's existing diffusers venv means vendoring `ZImageControlTransformer2DModel`/`ZImageControlPipeline` from videox_fun or the fal/neuralvfx ports (all are diffusers-style modules, so SDPA applies).
- 16 GB budget: Z-Image-Turbo (6B bf16 = ~12 GB weights) + full union ControlNet (15 of the blocks duplicated) will not fit with the Qwen3 text encoder resident; the **lite** 2601 union (1.9 GB, 3 blocks) or pre-encoding prompts and offloading the text encoder is the realistic configuration. klein-4B + LoRA fits (~13 GB stated) only with `enable_model_cpu_offload`, as the project already does.
- None of the clean 2D models emits PBR. Every open pipeline that claims PBR (Paint-it via SDS, StableGen via Marigold-IID/StableDelight decomposition, Paint3D via a UVHD de-lighting model) bolts on a separate decomposition. The fastest clean route is: generate albedo-looking views with "flat lighting / albedo / no shadows" prompting, then de-light + roughness/metal estimation in UV space with the project's existing tools (the sources above do not evaluate which decomposition is best).
- Qwen-Image-Edit-2509/2511 (Apache) is the strongest clean editor with native depth/edge/pose conditioning via extra input images and a built-in "new viewpoint" LoRA, but at 20B it is a 4-bit-only citizen on 16 GB (Nunchaku `svdq-fp4` is the Blackwell-native build), roughly 10x slower per view than Z-Image-Turbo. Qwen-Image-2.1 and 2.0 are out (research licence / API-only).

### Gaps
- No source gives measured VRAM or seconds-per-image for Z-Image-Turbo + Fun-ControlNet-Union on a 16 GB card, nor whether VideoX-Fun has been run on torch 2.8/sm_120.
- Whether the refcontrol-4B depth LoRA generalises to full-body game characters and props at 1024-2048 px is undocumented (author: trained mainly on humans; no benchmarks).
- No Apache-licensed normal-map ControlNet for Z-Image or klein-4B was found; no official BFL control tools for FLUX.2 klein.
- Qwen-Image-Edit-2511's card does not restate native ControlNet support (2509's does); whether 2511 still accepts a depth map as an input image was not verifiable from primary sources.
- Lumina-Accessory's licence (repo page shows none) and whether its "spatial conditional generation" includes depth are unconfirmed.

## KQ2. How open projects achieve multi-view consistency without a 3D-native model, and which approach has the best quality/cost on 4-8 views of a game character

### Takeaway
Four families are in use: (1) sequential project-and-inpaint (TEXTure, Text2Tex, StableGen "Sequential", StableProjectorz), (2) synchronised UV-space latent denoising (SyncMVD, TexFusion, TexPainter's optimisation variant, GOATex on top of SyncMVD), (3) multi-view grid generation with shared seed/IP-Adapter (StableGen "Grid", MVPaint, Meta TextureGen, FlexPainter's 2x2 grid), (4) cross-view attention/reference attention (SyncMVD's modified self-attention, StableGen's IP-Adapter-without-reference trick). The best-evidenced quality/cost for a handful of views is **UV-space latent synchronisation**: SyncMVD beats TEXTure/Text2Tex on FID (50.3 vs 74.4/71.2) and on every user-study axis except "more details", takes 60-150 s for 10 views on SD1.5, and is the base that later work (GOATex, MVPaint, FlexPainter) builds on; grid methods are fastest but documented to ghost after reprojection, and sequential inpainting is documented to drift.

### Cited Findings
- **SyncMVD mechanism** (SIGGRAPH Asia 2024, arXiv v2 Mar 2025): 10 orthographic cameras (8 on the equator at 45 deg + 2 elevated); SD1.5 + ControlNet v1.1 depth and normal via diffusers; 96x96 latent per view, 512x512 latent UV texture; at every denoising step the predicted clean views are projected into a shared UV latent texture and blended with cosine-similarity (view-direction vs normal) weights whose exponent rises linearly over the schedule (uniform early for consensus, direct-facing later for detail); gaps filled by Voronoi propagation masked by per-view triangle visibility; self-attention modified so each view attends to itself, its neighbours, its mirrored view and a reference front view until a switch step, then reference attention is weighted by beta and disabled; the last steps run unsynchronised in screen space; final RGB aggregated with alpha=6; **60-150 s per mesh** to denoise (GPU unstated); UVs auto-unwrapped with xatlas by default — [SyncMVD paper HTML](https://arxiv.org/html/2311.12891v2). The repo says it uses the mesh's existing UVs from .obj/.mtl, with xatlas only for meshes that lack them; keep meshes < ~40k faces; avoid overlapping UVs — [SyncMVD repo](https://github.com/LIU-Yuxin/SyncMVD).
- **SyncMVD results**: FID 50.26 vs TexFusion (simulated) 62.82, TEXTure 74.36, Text2Tex 71.20, Paint3D 72.01, Meshy 82.24; user study first-place votes: natural colour 39.1% (TEXTure 9.4%, Text2Tex 10.2%), fewer artifacts 42.8% (11.5% / 9.2%), 3D consistency 37.1% (8.3% / 16.2%), more details 20.0% (behind Meshy 22.6% and TEXTure 21.4%) — [SyncMVD paper HTML](https://arxiv.org/html/2311.12891v2).
- **SyncMVD limitations**: lighting is baked into the texture; the base model prefers canonical views so unseen sides can get wrong content (a car's grille on its underside); colour bleeding at depth discontinuities — [SyncMVD paper HTML](https://arxiv.org/html/2311.12891v2).
- **Independent comparison (FlexPainter, Jun 2025)**: text-to-texture FID/KID(x1e-4)/user preference: TEXTure 78.3/107.1/4.4%, Text2Tex 89.0/94.4/11.3%, **SyncMVD 73.4/41.7/22.5%**, Paint3D 77.8/123.6/17.8%, TEXGen 72.9/61.7/15.7%, FlexPainter 71.6/58.5/28.3% (SyncMVD has the best KID of all) — [FlexPainter HTML](https://arxiv.org/html/2506.02620v1).
- **Failure modes per family (FlexPainter related work)**: sequential per-view generation then fusion (TEXTure, Text2Tex): "views are generated independently, so inconsistencies arise easily"; synchronised UV-space denoising (SyncMVD, TexFusion): non-overlapping views never exchange information -> Janus problem; multi-view grid generation (Meta TextureGen, MVPaint, FlashTex): misalignment after reprojection to UV causes **ghosting**, and heuristic weight maps are brittle — [FlexPainter HTML](https://arxiv.org/html/2506.02620v1). FlexPainter itself uses a 2x2 grid of four views on FLUX.1-dev with a rank-256 LoRA, depth concatenated with the noisy latents, per-step reprojection sync plus a learned WeighterNet, TEXGen completion and Real-ESRGAN 4x (1K -> 4K); no code link on the page — [FlexPainter HTML](https://arxiv.org/html/2506.02620v1).
- **TexPainter** (SIGGRAPH 2024): optimisation-based colour fusion alongside DDIM that back-propagates into the latents to enforce consistency and removes the sequential dependency among views — [TexPainter arXiv](https://arxiv.org/html/2406.18539v1); needs "at least ... 24 GB" GPU, tested on RTX 3090; "within 5min" only with `--opt_eps 0` (default is 20 optimisation epochs) — [TexPainter repo](https://github.com/Quantuman134/TexPainter).
- **GOATex** (NeurIPS 2025): builds on SyncMVD's MVD module with SD1.5 + depth ControlNet, no fine-tuning; 16 hemispherical views (8 equatorial + 8 elevated at 45 deg) + 1 top camera; xatlas "superfaces", multi-view ray casting assigns each superface a hit level (max 4) so interiors/occluded layers are textured separately with their own prompt; soft UV-space blending with abs-cosine visibility confidence, per-level softmax; renders 768x768, latent UV 512, final UV 1024; ~12 GB VRAM per inference on an RTX A6000; 5k-face mesh: ~260 s hit-level assignment + ~118 s texturing per level; GPT-judge win rate over SyncMVD 91.2% for the full method; **no code release described** (arXiv licence CC BY-NC-SA 4.0 for the paper) — [GOATex HTML](https://arxiv.org/html/2511.23051v1).
- **Grid / shared-seed in production tools**: StableGen "Grid" mode combines all views into one grid for a single generation pass with an optional refinement pass; "Sequential" uses visibility masks and inpainting (differential diffusion, mask blur/grow options) with context renders of the previous state; IP-Adapter "can also run without a reference image to improve consistency in multi-view modes"; README recommends Sequential + IPAdapter for consistency; weighted blending with angle-based discard and blend-weight exponents; colour matching (MKL, Reinhard, Histogram, MVGD) before blending — [StableGen README](https://github.com/sakalond/StableGen). Developer's character demo (26 Oct 2025): "Characters" preset, six cameras around the character, SDXL checkpoint; the developer found FLUX.1-dev hard to get working well on limited VRAM and SDXL more reliable — [CGWorld article](https://cgworld.jp/flashnews/01-202511-StableGen.html).
- **2D editors as multi-view engines**: Qwen-Image-Edit-2511 integrates a community "new viewpoints" LoRA into the base model — [Edit-2511 card](https://huggingface.co/Qwen/Qwen-Image-Edit-2511); a "Multiple angles" LoRA for Edit-2509 accepts 1-3 reference images — [runcomfy LoRA page](https://www.runcomfy.com/models/qwen/qwen-edit-2509/lora/multiple-angles); BAGEL lists "multiview synthesis" — [BAGEL card](https://huggingface.co/ByteDance-Seed/BAGEL-7B-MoT). No source evaluates their pixel-level alignment to a given mesh.
- **User-reported quality** (secondary): a 2026 tool roundup links two r/StableDiffusion threads (664 and 1,274 upvotes) showing Blender mesh-to-texture and reference-projection results; the main criticisms were "baked highlights in the albedo map" and high polygon counts — [stacksheriff roundup](https://stacksheriff.com/ai-tools/ai-texture-generation-tools/?format=md). A render-farm article (marketing) says StableProjectorz "shines on organic surfaces such as character skin, oxidized metal, and fabric" but struggles on hard-surface geometry, seams need manual clean-up on complex geometry, and most runs take 2-5 min on an RTX 4090 — [superrendersfarm](https://superrendersfarm.com/article/stable-projectorz-3d-texture-generation-ai).

### Inferences
- For 4-8 views of a character, UV-latent synchronisation is the only approach with peer-reviewed evidence of both fewer seams and better FID at low cost (~1-2.5 min on SD1.5-class compute). Its two ingredients map directly onto what the project already owns: per-step projection of predicted x0 into UV space and back (the pure-torch UV rasterizer + depth-tested back-projection), and a visibility-weighted blend. It is model-agnostic in principle (it operates on predicted clean latents), so it can be re-implemented on Z-Image-Turbo's 16-channel latent space; the modified self-attention part requires patching attention processors, which diffusers' `set_attn_processor` supports.
- Cost scaling: synchronised denoising batches all views per step, so VRAM scales with views x resolution. SyncMVD's 10 views at 96x96 latents ~= 768 px; at 1024-2048 px per view on a 6B DiT the batch must be chunked per step (one forward per view, then sync), which turns 8 steps x 8 views into 64 sequential DiT forwards + 8 projection rounds -> still minutes, not hours, on a 5080 (Z-Image-Turbo is sub-second per 1024 image on H800 per its card; consumer-GPU timing is unmeasured).
- Grid mode (one 2x2/2x3 image, shared seed) is the cheapest way to get coarse colour/style agreement from a distilled model, but the ghosting-after-reprojection finding means it should be used only as the first pass, followed by a synchronised or sequential refine at full resolution — which is exactly StableGen's "Grid + refinement pass" design.
- Sequential inpainting (TEXTure-style trimap keep/refine/generate) remains necessary for the **unseen** regions after any sync pass, because sync only agrees where views overlap; the Z-Image union's inpaint mode or SDXL ProMax inpaint supplies the inpainting model.

### Gaps
- No published comparison of SyncMVD-style sync on a modern DiT (Z-Image, klein, Qwen) vs SD1.5; all numbers above are SD1.5/SDXL/FLUX.1-dev era.
- No measured timings for StableGen Grid vs Sequential; the add-on logs them to `stablegen_batch_log.json` but none were published.
- No primary Reddit/user-study evidence tied to a named tool on characters; the roundup's two threads are not confirmed as StableGen output.

## KQ3. Masked local edits ("make the shield rusty", "change the shirt colour"): which editing model + projection approach works, and how unseen/occluded areas are handled

### Takeaway
No open project does instruction-based, mask-local, multi-view-consistent texture editing end to end. The working recipe in production tools is: render the current texture from the edit view -> 2D edit (Qwen-Image-Edit-2509/2511 or FLUX.2-klein-4B multi-reference, both Apache) or masked inpaint (Z-Image union inpaint / SDXL ProMax inpaint) -> project back only through the user mask with angle- and silhouette-feathered weights (StableGen "Local Edit") or "WhereEmpty" masks (StableProjectorz) -> fill the leftover unseen UV area from surrounding texture (StableGen "UV Inpaint"). TexEditor (Mar 2026, Qwen-Image-Edit-2509 fine-tune) shows the specific 2D problem — editors regenerate the subject instead of changing only its texture — and improves structure retention from 0.64 to 0.93 on its benchmark; GOATex shows how to reach occluded layers (ray-cast hit levels), but neither ships a licence-clear mesh-editing tool.

### Cited Findings
- **Structure drift in 2D editors**: TexEditor's authors report SOTA editors "frequently struggle to maintain structural consistency during texture editing" and "tend to regenerate the edited subject"; TexEditor is built on Qwen-Image-Edit-2509 (Edit-R1 codebase, no architecture change), trained on 5,000 Blender pairs from 3D-FRONT where only the texture changes, with an SSIM reward on wireframe/edge maps (StructureNFT); TexBench texture scores instruction/structure/TexEval 0.858/0.929/0.886 vs Qwen-2509 0.767/0.642/0.717; baselines include Qwen-2511 and Nano Banana; single-image only; code/data link given (github.com/KlingAIResearch/TexEditor), **licence not stated** — [TexEditor HTML](https://arxiv.org/html/2603.18488v1).
- **Qwen-Image-Edit-2509** supports 1-3 input images (concatenated) and native depth/edge/keypoint/sketch conditions; **2511** adds "improved character consistency, reduced image drift" and built-in lighting-control / new-viewpoint LoRAs; both Apache-2.0 — [Edit-2509 card](https://huggingface.co/Qwen/Qwen-Image-Edit-2509), [Edit-2511 card](https://huggingface.co/Qwen/Qwen-Image-Edit-2511).
- **FLUX.2-klein-4B** multi-reference editing is native, but "every edit starts from pure noise" (no denoise-strength img2img) and there is no inpaint mode or ControlNet — [klein-4B card](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B), [comfy.icu node notes](https://comfy.icu/node/FluxKleinControlNetImg2Img).
- **Inpaint-capable clean models**: Z-Image-Turbo-Fun-Controlnet-Union 2.1 supports inpainting (`predict_i2i_inpaint_2.1.py`, larger control scale) — [2.1 card](https://huggingface.co/alibaba-pai/Z-Image-Turbo-Fun-Controlnet-Union-2.1); SDXL xinsir ProMax adds Image Inpainting/Outpainting — [xinsir union](https://huggingface.co/xinsir/controlnet-union-sdxl-1.0); Lumina-Accessory lists infilling/restoration and instruction editing — [Lumina-Accessory](https://github.com/Alpha-VLLM/Lumina-Accessory); OmniGen2 and BAGEL are instruction editors (Apache) — [OmniGen2](https://huggingface.co/OmniGen2/OmniGen2), [BAGEL](https://huggingface.co/ByteDance-Seed/BAGEL-7B-MoT).
- **StableGen Local Edit / UV Inpaint**: "Local Edit" blends the new texture over the original using angle-based and vignette/silhouette feathering with separate controls for angle ramp and silhouette edges; "UV Inpaint" fills untextured UV areas using surrounding texture context; "Refine (img2img)" restyles an existing texture; Qwen Image Edit is wired into Local Edit mode (installer offers a Lightning-LoRA and an Int4 Nunchaku variant) — [StableGen README](https://github.com/sakalond/StableGen).
- **StableProjectorz masks**: img2img inpaint masking limits projection to selected areas; "WhereEmpty" mode masks surfaces that have not yet received a projection; seams removed by dilating textures by 5 px; blending by painting on the model; per-projection hue/saturation/value/contrast — [stableprojectorz.com](https://stableprojectorz.com/); the Unity source describes an accumulation UV render texture, "bake projections with depth respected, dilate to handle seams", and user masks stored per generation record — [StableProjectorz repo](https://github.com/IgorAherne/StableProjectorz).
- **TEXTure** editing: trimap partition of each render into three progression states; "refine" mode re-generates regions where scribbles differ (scribble-based editing) and supports texture transfer between meshes — [TEXTure repo](https://github.com/TEXTurePaper/TEXTurePaper). **Text2Tex** uses a generation mask with generate/update/keep/ignore regions (non-commercial licence, see KQ4) — [Text2Tex repo](https://github.com/daveredrum/Text2Tex).
- **Occluded/interior regions**: GOATex assigns faces a depth-ordered hit level by multi-view ray casting, flips normals with backface culling to expose inner layers, textures each level separately with its own prompt, and merges with visibility-confidence softmax weights in UV space — [GOATex HTML](https://arxiv.org/html/2511.23051v1). SyncMVD's Voronoi fill propagates texels into UV regions no view covers, masked by triangle visibility — [SyncMVD paper](https://arxiv.org/html/2311.12891v2).

### Inferences
- For a masked edit the cleanest stack on the target machine is: (1) render the current albedo + depth from the 1-3 cameras that best see the masked faces (the project's UV rasterizer gives the per-face visibility, so camera choice is automatic); (2) edit with Qwen-Image-Edit-2511 (4-bit, with the rendered depth as a second input image to pin structure) or, cheaper, Z-Image-Turbo union inpaint with the rendered RGB as context and the depth as control; (3) back-project only inside mask x visibility x (cos angle)^k; (4) for mask faces no camera saw, run a second pass from new cameras with the first pass projected as context (sequential inpaint), then UV-space inpaint any residue. This is StableGen's Local Edit + UV Inpaint pipeline re-expressed on the project's own rasterizer, with no GPL code reused.
- TexEditor is the right *model* idea (a Qwen-Edit fine-tune that keeps structure) but its weights/licence are unknown; a cheaper substitute is prompting Qwen-Edit with the depth/edge map as an extra input image, which 2509 documents natively.
- FLUX.2-klein-4B is less suited to masked edits than to whole-view restyles: it has no inpaint/denoise control, so partial edits would have to be composited in image space before projection.

### Gaps
- No quantitative study of masked texture editing on meshes (consistency across views after a local edit) was found for any open tool.
- TexEditor's weight availability and licence are unverified (only a GitHub link in the abstract).
- No source measures Qwen-Image-Edit-2511 4-bit quality degradation on fine texture detail at 1024-2048 px.

## KQ4. Best open implementation to port (licence, code quality, dependencies), and realistic VRAM/time on a 16 GB card at 1024-2048 px views

### Takeaway
**SyncMVD (MIT)** is the best porting base: diffusers-native, ~50 commits of plain PyTorch, PyTorch3D used only as the rasteriser/projector (replaceable by the project's pure-torch UV rasteriser), xatlas optional because it honours existing UVs, no nvdiffrast/kaolin/xformers, 60-150 s per mesh for 10 views on SD1.5. Everything else is worse on at least one hard constraint: Text2Tex is CC BY-NC-SA 3.0 (banned), Paint-it pins nvdiffrast v0.3.0 and smplx (banned), TEXTure needs Kaolin 0.11 (CUDA extension, NSCL-licensed `non_commercial` module), Paint3D needs Kaolin 0.13 + PyTorch3D + its own SD1.5 UV-position ControlNet, TexPainter needs 24 GB and minutes of optimisation per mesh, MVPaint has no LICENSE file at `main` and rides on MVDream, GOATex/FlexPainter have no code. Realistic cost after porting to Z-Image-Turbo: 8 views x 8 steps with chunked per-view forwards plus per-step UV sync should land in the low minutes per asset at 1024 px, with the lite union ControlNet and an offloaded text encoder to stay under 16 GB; 2048 px views are only affordable as a final per-view Tile-SR/refine pass, not in the synchronised loop.

### Inferences
- What has to be swapped to make SyncMVD clean and run on the target stack: (1) PyTorch3D rasteriser/projector -> the project's `uvraster` + depth-tested back-projection (SyncMVD needs only forward rasterisation of per-view UV/visibility maps, no gradients); (2) SD1.5 + openrail ControlNets -> Z-Image-Turbo + Fun-ControlNet-Union (Apache) or SDXL + xinsir union (OpenRAIL++/Apache), re-deriving the x0-prediction hook for flow matching (predict x0 = x_t - sigma*v) and the 16-channel latent UV texture; (3) the modified self-attention -> a diffusers attention processor on the Z-Image transformer; (4) Python 3.8/conda -> the project's 3.12 venv. Nothing in SyncMVD requires nvdiffrast, kaolin, xformers or Linux-only tooling once PyTorch3D is gone.
- VRAM/time estimate for a 16 GB card after that port (no source measures this; derived from the anchors): per-view chunked DiT forwards at 1024 px, 8 steps x 8 views = 64 forwards plus 8 UV sync rounds; with Z-Image-Turbo at sub-second-per-image on H800 and 13-16 GB resident weights, expect 1-3 min per asset at 1024 px; a 2048 px Tile-SR/refine pass per view adds roughly the same again. Synchronised denoising at 2048 px for all views at once is not feasible in 16 GB (SyncMVD's 10-view batch at 96x96 latents already needs the whole batch resident); 2048 must be a per-view refine with the previous pass projected as context.
- If SDXL is chosen instead (xinsir union has Normal + inpaint ProMax, 8 GB class), the existing SyncMVD code port is nearly mechanical (same UNet/VAE family, 4-channel latents, diffusers ControlNet pipeline), at the price of SDXL's weaker prompt adherence and the OpenRAIL++ use-restriction list.

- No source reports SyncMVD or any latent-sync method running on Windows natively, on torch 2.8, or on a DiT base; all porting-cost statements above are inferences.
- No measured VRAM for Z-Image-Turbo + full union ControlNet at 1024/2048 px.
- MVPaint's licence could not be determined (no LICENSE file found).
- TexPainter's and TEXTure's output texture resolutions are not stated in their READMEs.

## KQ5. What StableProjectorz and StableGen do internally (models, projection, inpainting order, seam handling) and their licences

### Takeaway
**StableGen** (Ondřej Sakala, CTU Prague bachelor's thesis defended 19 Jun 2025; GPL-3.0; last README update 12 Jun 2026) is a Blender 4.2-4.5 / 5.1+ add-on that builds ComfyUI workflows (SDXL main, Qwen-Image-Edit, FLUX.1-dev and FLUX.2-klein experimental) with Depth/Canny/Normal ControlNet units + IP-Adapter, generates per-camera or grid images, projects them in Blender via OSL (4.x) or GPU Raycast nodes (5.1+) with visibility masks, blends by angle-weighted exponents after colour matching, and bakes to UV (Smart UV Project by default, PBR split via Marigold-IID/StableDelight nodes; TRELLIS.2 native mode uses nvdiffrast/nvdiffrec and is flagged non-commercial). **StableProjectorz** (Igor Aherne, Unity app, v2.4.5; relicensed **AGPL-3.0 in January 2026**, source on GitHub) talks to A1111/Forge over JSON, generates from scene depth with Depth ControlNet on by default (normals/inpaint/style-transfer ControlNets optional), projects each image through a ProjectorCamera into an accumulation UV render texture with depth testing, uses "WhereEmpty" masks to inpaint only untextured surfaces, dilates 5 px for seams, and preserves the original UVs/UDIMs.

### Cited Findings

**StableGen**
- Licence GPL-3.0; Blender 4.2-4.5 (OSL projection) and 5.1+ (GPU raycast-node projection), 5.0 unsupported; Windows 10/11, Linux, macOS; ComfyUI backend at `127.0.0.1:8188`; texturing architectures SDXL, Qwen Image Edit (installer options incl. **StableProjectorz**
- v2.4.5; free; "Open source under AGPL-3.0 as of January 2026"; outputs: textures may be used commercially subject to the third-party tools' terms, no guarantee given; backends listed: Automatic1111, ComfyUI, StabilityAI, Forge (installer sets up Forge; "roughly twice as fast" than legacy A1111); models: SDXL noted with depth-related fixes, Depth ControlNet on by default, Normals/inpaint/style-transfer ControlNets mentioned, several GB of ControlNets downloaded by the installer; projection: cameras snap to 45 deg, batches of art generated from scene depth and projected automatically; inpaint masking limits projection to selected areas, "WhereEmpty" masks untextured surfaces; "Multi-View Projection" textures the whole object in one pass; seams removed by dilating textures 5 px; blending by painting on the model; "Preserves UVs", UDIM supported; requirements GTX 1080+, 12 GB RAM, Windows implied by EXE installer; author Igor Aherne (sole developer) — [stableprojectorz.com](https://stableprojectorz.com/).
- Source: a Unity 6000 project (`Assets/_gm`), AGPL-3.0; "Talks to A1111/Forge via JSON"; sends depth, normals and vertex-colour images to Stable Diffusion; ProjectorCamera projects the AI image into an accumulation UV render texture; multi-view via "Perspective Shift" pins arranging several cameras in one viewport; render loop: clear, bake projections with depth respected, dilate for seams, display; generation records store user masks; an "Agent Bridge" TCP/JSON socket for MCP-style tools; queries an external WebUI for Trellis/Hunyuan 3D generation; Releases section empty, 35 commits — [IgorAherne/StableProjectorz](https://github.com/IgorAherne/StableProjectorz).
- A third-party ComfyUI bridge exists: StableProjectorz sends ControlNet images/masks and inpaint images/masks to ComfyUI, which processes and returns them; settings exposed via `ProjectorzParameter` / `ProjectorzControlnetParameter` nodes — [ComfyUI-StableProjectorzBridge](https://comfydeploy.com/comfy-node/tianlang0704/ComfyUI-StableProjectorzBridge).
- Earlier coverage described it as a free tool projecting Stable Diffusion art onto 3D models with brush-based blending and per-projection colour controls — [CGPress](https://cgpress.org/archives/stable-projectorz-an-ai-tool-for-3d-texture-generation.html).

### Inferences
- Both tools implement the same "generate from depth -> project through the camera with depth test -> accumulate with angle/visibility weights -> inpaint WhereEmpty -> dilate" loop that the project's existing back-projection already does; the differentiators are UX (brush blending, pins) and the ComfyUI/Forge model zoo. Neither uses latent synchronisation; StableGen's only cross-view coupling is the grid pass, IP-Adapter and sequential inpainting with previous-state renders.
- Licence consequence: GPL-3.0 / AGPL-3.0 code cannot be vendored into the MIT codebase; driving StableGen's ComfyUI workflows or StableProjectorz's Agent Bridge as separate processes is licence-compatible but drags in ComfyUI/Forge, Blender-side OSL/raycast projection and (for StableGen's TRELLIS.2 native mode) nvdiffrast. Re-implementing the method is cheap because the method is fully described in public READMEs.
