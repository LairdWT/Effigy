Acceptance: 4-view run ≤ 14.5 GB: **10.98 GB**. Silhouette-height consistency check: in `prep` op
`views`, the subject heights of the views must agree within `height_tolerance` (5 %); this sheet: 2.5 %
(perspective).

The result rendered with the same four cameras matches the input from every side, the hammer in the
right hand in all four (so the view naming and the c2w convention are right: "right" = the character's
right side, camera at −X).

## Where the memory went

The texture stage's conditioning, profiled per part (4 views, standalone): DINOv3 1.3 s, projection
3.2 s, NAF 28.3 s; NAF's 1024² output dominated. Upstream's NAF attention holds the values upsampled to
full resolution, the attention output and its rearranged copy at once (3 × 4 GiB at 1024 channels); the
multi-view extractor added a view-sized `[lr | hr]` concat beside its running sum (2 GiB). In the full
pipeline that reserved 17.4 GB on the 16 GB card and the conditioning crawled in shared memory. Both are
runtime patches (`engine/trellis2/PATCHES.md` rows 14 and 15), each tested equal to upstream on the CPU;
single-view Faithful takes patch 15 too.

## Ingestion

`prep` op `views`: a sheet split into equal columns, or `sources` (one upload version per view, resized
to the first's height); one crop size for every view (the cameras share a distance); `view_<k>.png`,
`cameras.json` (c2w per view, view 0 = front); `image.png` = the front view so single-view steps keep
working. UI: "Views in the picture" on the image upload (5 sheet orders). `trellis2` uses all views when
`weights: faithful` and the prep version has `cameras.json` (`multiview: false` → the front only).

(the M18 characters, before patch 15) were fine; patch 15 is exact by test, so the input is the likelier cause.
