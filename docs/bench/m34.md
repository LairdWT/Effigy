# M34: motion from video (2026-10-08, in progress)

The `mocap` step (`steps/mocap.py`, `.venv-gemx`, model group `mocap`) run from the command line on the owner's
test clip (a stock dance clip, 14.2 s, 30 fps, 2160 × 3840 portrait), in a scratch folder laid out like a
library asset; the GEM-X spike and the mode comparison are in `docs/research/12-video-to-motion.md`.

## The step on the dance clip (Best mode)

| | |
|---|---|
| clip as GEM-X sees it | 426 frames, 720 × 1280 (from 4K), 30 fps |
| total time | 105 s (GEM-X's stages 101 s: YOLOX on the GPU, ViTPose, SAM 3D Body, 50 DDIM steps; model loading included) |
| peak VRAM | 4.31 GB |
| facing turn | 174.0° (GEM-X's world had the dancer facing −Z; the spike measured 175.7°) |
| foot slide while planted | 0.167 m/s before the foot lock, 0.110 m/s after (75 frames held) |
| root jitter | 5.19 mm (mean second difference) |
| outputs | `motion.bvh` (78 SOMA joints, upright rest), `clip.glb` (78 bones, `blender_ops/bvh_clip`), `preview.mp4` |

Found on the way, fixed before these numbers: forward kinematics took SOMA's bind-pose joint positions as
offsets (the floor, the facing turn and the foot lock ran on wrong joints; the BVH itself was right: its writer
makes its own offsets); now pinned by `tests/test_mocap.py::test_fk_uses_bones_not_positions`. The person
detector on the GPU: ONNX Runtime 1.30 is built for CUDA 13 and fell back to the CPU (110 ms a frame); 1.23 with
torch's CUDA 12.8 DLLs preloaded: 10.6 ms.

The first 5 s of the same clip (after the review fixes: every model file checked first, Hugging Face offline,
DINOv3's code loaded as a local repo): 150 frames, 115.9 s, 4.31 GB, foot slide 0.239 → 0.144 m/s. Loading the
models (ViTPose 3.4 GB, SAM 3D Body 2.1 GB, GEM-X) dominates: a 5 s and a 14 s clip take about the same time.
ponytail: one-shot; a resident worker (as M30 did for text-to-motion) when several clips in a row matter.
